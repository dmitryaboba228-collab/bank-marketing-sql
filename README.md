# Телемаркетинг банка: от плоского CSV к базе и решению

Португальский банк обзвонил 45 211 человек, предлагая срочный вклад.
Согласились 11.70%. Три четверти времени колл-центра ушло в никуда.

Проект отвечает на вопрос: **кому звонить, а кому не стоит** - и во что
обходится каждый лишний звонок.

Стек: **PostgreSQL 18**, pgAdmin, Python (matplotlib, psycopg2).

**-> [analysis.ipynb](analysis.ipynb) - весь анализ: запросы, код, графики и выводы в одном файле.**

---

## Задача

Исходные данные - одна плоская таблица на 17 колонок. Из неё нельзя задать
бизнес-вопрос: клиент как сущность не существует, справочники размазаны по
текстовым полям, история прошлых контактов закодирована заглушками.

Работа состояла из трёх частей:

1. **Спроектировать схему** - разложить плоскую таблицу в третью нормальную форму
2. **Загрузить данные** - ETL с проверкой целостности до загрузки
3. **Ответить на вопросы бизнеса** - 30 SQL-запросов, от проверки качества
   данных до расчёта экономии

---

## Данные

[UCI Bank Marketing](https://archive.ics.uci.edu/dataset/222/bank-marketing) -
реальные данные телемаркетинговых кампаний португальского банка,
**май 2008 - ноябрь 2010**. Лицензия CC BY 4.0.

Данные обезличены: имён, идентификаторов и контактов в источнике нет.
Имена и фамилии в `raw/bank-full-named.csv` **сгенерированы** скриптом
`src/add_names.py` (португальские, фиксированный seed) - исключительно чтобы
карточка клиента выглядела правдоподобно. Все остальные значения - подлинные,
изменению не подвергались.


* Контактов: 45 211 
* Звонков всего: 124 956 
* Согласий: 5 289 (11.70%) 
* Период: 30 месяцев 
* Время разговоров: 3 242 часа 

---

## Схема

Восемь таблиц: пять справочников, карточка клиента, контакт текущей
кампании и история прошлой.

```
jobs ─────────────┐
marital_statuses ─┤
education_levels ─┼─< clients >─┬─ contacts >─ contact_channels
                  │             └─ previous_campaign >─ campaign_outcomes
```

- `clients` - 45 211 строк, карточка и финансовый профиль
- `contacts` - 45 211 строк, связь 1:1, итог текущей кампании
- `previous_campaign` - **8 257 строк**, только клиенты с реальной историей

## Ключевые выводы

Подробно, с графиками и запросами - в [analysis.ipynb](analysis.ipynb).

**Ограничение обзвона четырьмя попытками экономит 27 275 звонков (21.8% всей
нагрузки) ценой 392 согласий (7.4% продаж).** Конверсия падает с 11.70% до
10.83%. Экономия ресурсов перевешивает потери в три раза.

Первый звонок приносит 48.4% всех продаж, первые четыре - 92.6%.

Клиенты с историей контактов конвертируются в 2.5 раза лучше: 23.07% против
9.16%, составляя 18% базы, они дают 36% продаж.

Зависимость конверсии от возраста U-образная: 23.95% у молодых, минимум 9.35%
в группе 46-55 лет, максимум 42.61% у клиентов старше 65.

## Решения, которые пришлось принять

**Отсутствие истории выражается отсутствием строки.** В источнике клиенты без
прошлых контактов помечены заглушками `pdays = -1`, `previous = 0`,
`poutcome = 'unknown'`. Хранить их означало бы записать `-1 день` как факт.
В `previous_campaign` попали только 8 257 клиентов с реальной историей,
остальные 36 954 представлены отсутствием записи - отсюда `left join`
в половине запросов.

**`duration_sec` - утечка целевой переменной.** Длительность звонка неизвестна
до звонка. Три контакта нулевой длительности все закончились отказом. Колонка
хранится для анализа затрат, но в выводах о том, кому звонить, не участвует.

**Канал `unknown` - не канал.** 13 020 записей (28.8%) не имеют указанного
способа связи. Это пропуск в данных, а не третий вид связи, поэтому сравнение
каналов проводится только между `cellular` и `telephone`.

**Год восстановлен, а не дан.** В источнике года нет - только день и месяц.
Год восстановлен из хронологического порядка строк: там, где номер месяца
уменьшается, произошёл переход через декабрь (`sql/03_restore_year.sql`).
Метод опирается на допущение, что строки идут по времени; допущение
проверяется границами периода - май 2008 и ноябрь 2010.

**Порог достоверности групп.** В разрезах, где встречаются группы по
100-200 человек, конверсия скачет от случайности. Во всех выводах используются
только группы от 300 клиентов.

## Как запустить

Подготовка данных:

```bash
python3 src/etl.py       # плоский CSV -> восемь нормализованных CSV
python3 src/validate.py  # 38 проверок целостности до загрузки
```

### Вариант А: свой сервер PostgreSQL

Данные кладутся в общедоступный каталог, потому что серверный `copy` читает
файлы от имени пользователя, под которым работает PostgreSQL:

```bash
mkdir -p /Users/Shared/bank_data && cp data/*.csv /Users/Shared/bank_data/
```

### Вариант Б: контейнер

Ставить PostgreSQL не нужно, база поднимается одной командой:

```bash
docker compose up -d
```

Каталог `data/` монтируется внутрь по тому же пути, что и в варианте А,
поэтому `02_load.sql` работает без правок. Порт на хосте - 5433,
база `tbank`, пользователь и пароль `postgres`.

Дальше в pgAdmin или psql выполнить по порядку:

```
sql/01_schema.sql        создать восемь таблиц
sql/02_load.sql          загрузить данные, в конце печатает сверку
sql/03_restore_year.sql  восстановить год контакта
```

Загрузчик должен показать
`clients 45211 | contacts 45211 | previous_campaign 8257 | jobs 12`.

Запросы - в `sql/04_queries.sql`, индексы и замеры - в `sql/05_indexes.sql`.

### Notebook и графики

```bash
python3 -m venv .venv
.venv/bin/python -m pip install matplotlib psycopg2-binary jupyterlab
export PGHOST=localhost PGPORT=5432 PGDATABASE=tbank PGUSER=postgres
export PGPASSWORD=...
```

Открыть анализ и выполнить ячейки:

```bash
.venv/bin/jupyter lab analysis.ipynb
```

Графики вшиты в файл, поэтому на GitHub они видны и без запуска ядра.
Чтобы перестроить их на своих данных, выполни ячейки заново.

Пароль в коде не хранится - подключение читает стандартные переменные
окружения PostgreSQL.

## Структура

```
 analysis.ipynb                анализ, код и графики 
 raw/    bank-full-named.csv   исходник UCI + сгенерированные имена
 src/    etl.py                плоский CSV -> 8 нормализованных CSV
         validate.py           38 проверок: ключи, check, типы, длины
         add_names.py          генератор имён, seed = 42
 data/    *.csv                подготовленные к загрузке
 sql/    01_schema.sql         DDL: 8 таблиц, ограничения, комментарии
         02_load.sql           загрузка через copy со сверкой
         03_restore_year.sql   восстановление года из порядка строк
         04_queries.sql        30 аналитических запросов
         05_indexes.sql        индексы и замеры explain
```
